# Skill 的体裁：以认知叙事组织指导层

> Skill 不应只是动作的仓库。它首先要让执行者知道：此刻面对的是什么状态，为什么这条动作适用，什么会让它失效，以及怎样观察自己已经真正完成。

设计一个 Skill 时，人很容易从“我要放进哪些命令、规则和链接”开始。于是文档可能写得很完整：有安装命令、有执行步骤、有错误码、有注意事项。执行 Agent 也许能照着运行其中的一条命令，却仍会犯一种更隐蔽的错误：在不该运行的项目中运行，在前提不满足时重试，把退出码为零误读成任务完成，或者遇到例外时继续沿原路径硬走。

例如，一句“运行 `npm test`”并没有告诉 Agent：应在哪个项目根目录运行；这次测试要证明什么；哪些失败意味着代码问题、环境问题或不应继续；何种结果才足以支持“功能已验证”的后续判断。命令本身没有错，缺的是命令与任务状态之间的关系。

这正是“所有常规 Skill 是否都应写成认知叙事”值得认真讨论的原因。它不是偏好文章写得更有解释性，而是在问：Skill 是否必须把 Agent 从当前状态带到一个可验证、可暂停、可改走的行动能力。

## 先看 Skill 真正承担的工作

一份长命、可复用的文本型 Skill，通常不只是储存信息。它在任务现场改变 Agent 的选择、执行顺序、验收方式或停止条件。只要它承担这种指导职责，执行者至少需要恢复五件事：

```text
适用：为什么现在该使用它，而不是另一条路径
对象：当前要识别的项目、状态、输入或约束是什么
动作：这一步怎样使任务状态发生变化
验收：看见什么才算到达可依赖的下一状态
改走：什么信号要求暂停、恢复、升级或交回
```

这五件事组成的是一条行动理解路径。它不要求作者公开私有的思考过程，也不要求把每个命令译成散文；它要求与行动有关的判断关系能够被执行者重新定位。

本文所说的“认知叙事”，指的正是这种让行动判断关系可被重建的组织责任，而不是必须另写一篇线性散文。短入口契约、带有转移理由的路由表或状态机，只要完整呈现这五件事，也可以直接承担认知叙事的指导作用；长篇文字只是在需要修正理解模型、比较路径或显露取舍时的一种载体。

因此，认知叙事在 Skill 中的价值，不是“让规则更顺地被读完”，而是防止关键判断藏进一句命令、一个默认值或一段看似确定的步骤里。执行者应能解释：为什么此时应该这样做；改变一个关键条件后，为什么应改走；完成的证据又是什么。

## 全称主张在什么地方需要收紧

如果“所有 Skill 都写成认知叙事”指的是：每一行内容、每一个资源、每一个脚本都必须写成线性说明文章，这个主张不成立。

设想一个输入状态有限、合法状态可枚举、动作可重复验证的 Skill。它可以把分类写成决策表，把执行写成状态机，把字段写成 Schema，把机械动作交给脚本，把通过条件写成断言矩阵。只要这些载体明确呈现条件、动作、验证与失败去向，Agent 仍能正确选择和执行，不必为了查一个参数重读一篇解释文章。

这不是降低要求。恰恰相反，表格的条件列、状态机的转移守卫、Schema 的字段约束、断言的通过条件，往往比一段自然语言更精确、更可定位，也更容易自动验证。

所以需要区分三个层次：

| 层次 | 它负责什么 | 适合的体裁 |
| --- | --- | --- |
| 指导层 | 为什么适用、当前在什么状态、何时改走 | 短认知叙事，或完整承载五件事的入口契约、路由表、状态机 |
| 执行层 | 已知状态下怎样稳定地完成动作 | 程序、状态机、决策表、脚本 |
| 资源层 | 参数、字段、命令语法、错误码、样板 | 参考表、Schema、索引、模板 |

这里的关键不是给三层贴上好看的名字，而是避免职责偷渡。若脚本替人决定了价值取舍、授权边界或风险接受，它再确定也不应被当作纯执行层；这些判断必须回到指导层，在触发它们的状态转移处显露。反过来，若一张命令参数表只承担精确查值，就不应被叙事性解释淹没。

## 认知叙事是控制平面，不是全文的唯一材料

由此可以得到一个更强、也更可操作的结论：

> 当文本自身承担行动路由，且目标是在边界情境中仍可暂停、验证和改走时，它的指导层应让执行者重建五件事；整份 Skill 则应按内容职责组合叙事、状态机、表格、脚本、模板与参考索引。

“指导层”不是给一个原本不透明的 Skill 加一段背景介绍。它是控制平面：决定 Agent 要加载什么、要检查哪个状态、可以调用哪个执行资源、何时不得继续，以及结果怎样回写为下一次判断。

```mermaid
flowchart LR
  A[触发：任务与适用条件] --> B[指导层：状态、目标与分叉]
  B --> C[路由：选择状态机、表格、脚本或模板]
  C --> D[执行：产生状态变化或产物]
  D --> E[验证：观察结果、失败或未知]
  E -->|完成或改走| B
```

这张图不是要求每份 Skill 都画流程图。它说明一条责任链：表格、脚本和模板可以承载路径中的节点，却不能替代“为什么选择这个节点、结果意味着什么”的控制关系。

这种分层也保留了渐进加载的价值。首次使用时，Agent 先消费短而完整的指导主干，建立正确的问题模型；确定路径后，只加载当前所需的决策表、命令参考或脚本。重复使用时，可以直接从路由和状态进入，不必反复阅读解释。上下文预算因此服务于理解，而不是迫使作者删掉承重关系。

## 什么情形必须显露叙事关系

并不是每个动作都需要长解释，但会改变行动方向的转移必须可重建。一个实用的写法是把这类转移写成：

```text
触发信号 → 所需证据或前提 → 可选路径及取舍
→ 谁被允许作决定 → 如何验证 → 失败后回到哪里
```

其中“谁被允许作决定”尤其不能被脚本静默吸收。一个自动清理、发布、迁移或绕过审批的动作，即使技术上完全可执行，仍可能包含尚未被授权的价值判断。Skill 应说明脚本能做什么、不能决定什么、在什么条件下必须交回，而不是把这种边界藏进“自动化”的表象里。

同样，确定性不等于没有指导责任。脚本内部也许已经固定了从输入到输出的桥梁，但“何时调用它、输入代表哪种状态、退出码是否足以让下一步继续”仍属于指导层。只有外部控制器已经独立完成适用判定、权限校验、路径选择、验证和失败处置，且文本不再补充或改变其中任何一项时，文本才可降为自动化组件或参考资源，而不是这里所说的文本型常规 Skill。不能只因它短小、受平台约束，或碰巧放在一个目录里，就把尚未外包的判断当作已经被系统承担。

## 怎样为一份新 Skill 选体裁

设计时不必先问“这是不是一篇认知叙事”，而应从读者即将遇到的缺口开始。

先作一个最小判定：文本是否还要替执行者决定或解释“现在是否适用、走哪条路、能否继续、谁有权接受风险”？若答案是否定的，并且这些判断确已由可观察的外部控制器完成，文本可以只作为组件说明或参考资源。若答案是肯定的，先把五件事压缩成一个可扫描的入口；状态有限且转移可枚举时，这个入口可以就是路由表或状态机。只要其中出现模型修正、竞争解释、价值取舍或未冻结的授权边界，再用叙事文字展开相应的分叉，而不是因“状态有限”把这些判断一并删掉。

若 Agent 必须先修正旧模型、理解为什么一条材料改变了建议、辨认竞争解释，或在价值取舍之间改走，认知叙事应承担主干。研究、设计、复杂排障、跨团队协作、策略性工作流通常属于这一类。

若合法状态已经有限且可枚举，重点是同条件下稳定执行，就把状态和转移写成决策表或状态机，并让指导层说明这些状态为何重要、异常时去哪。测试、登记、格式转换、固定接口操作常包含这一类部分。

若内容只是参数、字段、命令语法或错误码，优先使用可检索的索引；不要让读者为了找到一个事实而顺读整条主线。若动作可以重复、可验证且不含未冻结的判断，把它固化为脚本；脚本旁仍要声明输入、输出、失败状态和它不负责的决定。

因此，体裁选择不是按“这是测试 Skill”“这是开发 Skill”这类名称完成，而是按每一段内容究竟在承担理解、路由、执行、查值还是生成的职责完成。

## 用它直接审查一份 Skill

当一份 Skill 已经写好，可以只问下面五个问题：

1. 第一次加载它的 Agent 能否判断此时是否适用？
2. 它能否定位当前动作的对象、前提和预期状态变化？
3. 改变一个关键条件后，它能否知道应停止还是改走，而不是机械复用步骤？
4. 它能否区分“命令执行完”与“任务目标已经验证”？
5. 价值、授权和风险边界是否在相应转移处可见，而不是藏在脚本、默认值或作者常识里？

前四问答不清，说明指导层缺少可重建的行动关系；第五问答不清，说明关键判断被错误地伪装成了执行细节。相反，若这五问已经由一张路由表、一个状态机或一个极短入口契约充分回答，就没有理由为了形式完整再增加一段长叙事。

## 这不是已经被实证证明的体裁排序

目前可以作出的，是一项结构性的内容判断，而不是“认知叙事在所有 Agent 上都更有效”的经验定律。

可以撤销的是“所有常规 Skill 的全部正文必须使用单一认知叙事体裁”这一全称必要性：存在保留正确选择、执行和验证能力的表格、状态机、断言协议与脚本组合。

可以暂时采用的，是一项面向鲁棒执行的设计规范：当文本自身承担行动路由，并希望执行者在边界情境中能够暂停、验证和改走时，指导层应让执行者重建适用、状态、动作、验收和改走关系。认知叙事是组织这组关系的直接形式，且能由非散文载体承载。

仍然未知的是：在相同 token 预算下，纯 checklist、纯状态机、以及“短认知叙事主干加原生执行资源”三种版本，究竟会怎样影响不同模型的首次成功率、边界情境改走能力、误用率和维护成本。这个问题需要在确定性操作、条件分支操作和应急恢复等不同任务中做对照，不能由文档的流畅程度代替。

## 结尾：把“写成叙事”改成“让判断路径可被使用”

“所有常规 Skill 都应写成认知叙事”之所以有力量，是因为它反对把 Agent 当成只会按按钮的执行器。更准确地说：一个承担行动路由的 Skill，应让 Agent 在任务现场拥有足以选择、验证、质疑和改走的理解，而不是碰巧复现作者写下的动作。

但这条主张真正要守住的，不是叙事文字的篇幅或形式，而是行动判断的可见性。让指导主干可重建行动判断关系，把精确动作交给状态机、表格和脚本，既不会把关键理解丢给 Agent 自行猜测，也不会把每一次查值和执行硬拉成文章。

Skill 因此不是“叙事或工具”的二选一。它是一种复合体：认知叙事负责让行动有方向，原生执行载体负责让方向可靠地落地。
