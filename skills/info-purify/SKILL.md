# Info Purify

本 Skill 的目标是让读者能利用已有信息完成任务，并让后续维护者有办法吸收变化。先确定需要回答的问题，再从材料中识别稳定的对象、概念、关系和必要约束，形成可消费的结构；用来源核对防止失真，用实际使用和更新演练检验是否有效。

“有序”在这里指：找到、理解、使用和更新信息所需的工作减少，关键事实、条件、例外和分歧仍被保留。文档更短、分类更多或目录变化，都不能单独证明有序。“降熵”是工作目标的比喻，不是测得的 Shannon 熵。

## 核心区分

| 内容 | 含义与例子 |
| --- | --- |
| 原始材料 | 可回溯的消息、文件、观察和版本。原话“计划周五上线”仍保留。 |
| 信息模型 | 说明材料描述什么、如何区分和关联的表示约定。比如“项目有负责人、计划日期和实际状态”，不同项目不能因同名而合并。 |
| 产物本体 | 交给读者使用的正文、表格、问答、索引或其他视图。比如显示项目当前进展，并能追查计划变更。 |
| 净化日志记录 | 记录结构选择、旧新映射、查证、测试和未决项，供复核而非日常阅读。 |

信息模型不是另一份全文台账，也不要求数据库或知识图谱。简单任务可以用几句组织约定表达；持续维护时，它必须有可定位、可更新的保存位置，不能只存在于本次思考里。正文和其他视图共同引用相同的信息依据，避免各自维护一套事实。

## 工作边界

可直接做：调整表示结构、统一有依据的别名、拆分混写、合并语义等价内容、显式表达关系、按证据更正或标记既有记录。

不得借整理擅自创设或改变业务规则、执行要求、现实权责、接口契约或价值取舍。此类问题记录为**升级候选**：需要另行研究或由有决定权的人裁决的问题。例如材料未决定谁批准上线，不能为了补全 SOP 自行指定。

区分两种变化：

- **信息模型演化**：为了正确表达既有材料，增加“适用版本”字段或拆开两个同名概念，属于净化范围；保留映射并复核受影响视图。
- **现实规则变更**：把“负责人批准”改成“任意成员批准”，超出净化范围。用户已明确授权这种改造时，作为单独的设计工作处理，注明授权与新决定，不能伪装成原文已有结论。

来源所述不自动等于现实真相；到达更晚的消息也不自动覆盖旧记录。关键冲突、来源适用范围和身份歧义，在依赖它们设计结构或宣布当前状态之前就要处理。

## 选择执行路径与强度

两个维度分别决定做什么、保留多少证据：

| 执行路径 | 适用条件 | 必要工作 |
| --- | --- | --- |
| 一次性重构 | 本次交付是确定范围的静态材料 | 建立足够的表示，重构产物，验证消费任务；不强制设计长期维护体系。 |
| 持续维护 | 用户要求持续增长、增量融入、反复更新同一体系，或正在向已有体系接入变化 | 除上述工作外，保存信息模型和依赖位置，执行更新规则并演练变化；首次建成后，后续调用优先局部更新。 |

| 执行强度 | 选择依据 | 证据规模 |
| --- | --- | --- |
| 轻量模式 | 小范围、低风险 | 合并记录来源、结构选择、变更和测试，不制造空表。 |
| 标准模式 | 多材料、多视图、后续复用 | 明确信息模型、关键记录与旧新映射，保留适用的核查结果。 |
| 审计模式 | 错误会影响执行、契约或高风险决策 | 对关键事实、规则、例外、冲突及影响链逐项核验，明确覆盖范围和独立复核结论。 |

“长期维护”本身不意味着必须输出全部审计表。无论强度如何，来源保真、关键风险和使用验证都不能省。领域无关字段可以省略并说明理由，不给每个概念强塞生产方、消费方或生命周期。

## 工作流程

开始时按以下阶段建立待办；用当前环境的计划工具或普通文本即可，不绑定特定工具名。首次重构通常依次推进；后续增量从阶段一核对范围，进入阶段四处理变化，必要时回到阶段二、三，再走核查、验证与收束。

进入某阶段时阅读对应文件。阶段一、二需要理解方法时读[信息净化方法](references/info-purify-method.md)；持续维护在阶段三、四、六读[增量维护规则](references/incremental-maintenance.md)。

| 阶段 | 要形成的状态 | 执行指引 |
| --- | --- | --- |
| 阶段一：任务与消费验证基线 | 明确读者任务、材料范围、不可改约束和可演示的验收任务 | [任务与消费路径](workflow/01-scope-and-consumption.md) |
| 阶段二：结构诊断与模型选择 | 识别使用障碍，选择足够而不过度的表示结构 | [诊断与选择](workflow/02-structure-diagnosis.md) |
| 阶段三：信息模型与消费视图 | 必要语义清楚，并有可使用的结构草案 | [模型与视图](workflow/03-target-structure.md) |
| 阶段四：信息整合与双向追溯 | 材料有明确去向，重要结论可回溯，变化可传播 | [整合与追溯](workflow/04-mapping-and-trace.md) |
| 阶段五：语义核查与专项交接 | 事实、概念、权威、关系和领域风险经过核查，未决问题有处理路径 | [核查与交接](workflow/05-validation-and-domain-checks.md) |
| 阶段六：产物生成与使用验证 | 读者任务实际走通；持续维护场景的更新演练也有结果 | [生成与验证](workflow/06-output-and-validation.md) |
| 阶段七：独立复核与交付收束 | 失败得到修复或明确限制可用范围，交付状态与证据一致 | [复核与收束](workflow/07-review-and-close.md) |

这不是一次走完就不能回头的流水线。身份或概念边界改变，回阶段二、三，并更新映射及相关视图；来源或权威改变，回阶段四、五；消费任务变化，回阶段一。回退时标记受影响的旧结论和测试失效，重做后才能恢复通过状态。

## 每次交付什么

用[信息包模板](templates/purified-info-package.md)按需组合，保持两类内容的边界：

- **产物本体**：读者可以直接使用的结果，含影响其行动的适用范围、例外、冲突和待确认说明。持续维护时附可用的模型与更新说明；可单独成文，也可置于现有维护文件中。
- **净化日志记录**：原结构障碍与结构选择依据、旧新映射或变更说明、来源追溯、查证与实际验证结果，以及未决项和交接状态。无专项问题或升级候选时写“未发现”，不用空表凑齐。

不是每次都要实质性改目录。经消费验证有效的原结构可以保留；增量更新只改相关部分。索引、表格或问答只要就是所需产物且确实支持目标任务，也可以完成交付；若用户需要完整正文，仅给索引仍不算完成。

## 完成判定

必须回答：目标任务实际完成了吗？关键含义保住了吗？本次改变或保留结构的理由是什么？持续维护路径下，新材料怎样进入、过期结论怎样退出、相关视图怎样同步？

独立复核按阶段七执行。有可用 Subagent 时委派只读复核；没有时自行按同一标准复核，注明“未进行独立复核”。不能把自检叫作独立复核。

输出状态用“通过 / 限定范围可用 / 未通过”，并写清证据与受阻任务。把阻断问题登记进风险清单，不等于该任务已经可用。不得以“已降熵”替代具体结果。
