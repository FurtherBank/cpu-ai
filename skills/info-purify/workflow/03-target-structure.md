# 信息模型与消费视图

## 输入与目标

输入阶段一、二产物、原始材料与已有结构。目标是得到能表达材料、服务任务的模型和视图草案，并能用例外修正它。

## 执行

1. 定义最少必要的表示约定。按任务选择对象或主张的身份、核心属性、关系、范围、证据和时间状态。写清同一对象如何认定、别名如何处理；仅名称相似不足以合并。为整理新增的查询标识须与来源中的正式编号区分，读者视图也要标明，不能只在内部模型说明。
2. 对会改变判断的概念说明定义、边界及易混对象。生产方、消费方、生命周期只在任务实际涉及这些关系时填写。材料未知就保留未知，不补造。
3. 区分来源明确陈述与整理者推断。关系至少说明方向、含义、适用条件及依据；“先发生”不能直接写成“导致”，“有建议”不能写成“已决定”。
4. 用代表性材料填入草案，保留例外与无法表示的材料。需要改变对象边界或关系含义时回阶段二重选，不能只加一个含混的“其他”目录。
5. 按消费任务设计产物本体：共同前提、核心内容、条件分支、细节、历史和必要风险。多视图从共享记录或明确来源生成，标出共同依赖的位置。
6. 持续维护路径阅读[增量维护规则](../references/incremental-maintenance.md)，确定模型与当前记录保存在哪、更新从哪进入、哪些依据支撑哪些视图。一次性任务保留本次必需的追溯即可。

## 产出

- 信息模型草案及其保存位置：可以是短说明、表格字段约定或关系结构，不要求专门技术系统。
- 消费视图草案及读者入口，必要时有视图到共同依据的链接。
- 结构改动说明：保留、合并、拆分、移动、上提、下沉、隔离及理由。
- 无归属材料、身份歧义、冲突、待确认或升级候选；每项写清影响哪个任务。

例如：同名“Atlas”分别是移动端和服务端项目，应先区别对象，项目总览可再聚合展示。不能因总览需要简洁而合并负责人和状态。

## 退出条件

主要任务已有对应视图；关键身份或语义歧义已解决，或被隔离且限制依赖它的结论。持续维护路径已能指出模型、记录和依赖位置，而非只写“以后持续更新”。
