# 感知型任务的验证

## 适用范围

以下案例来自用户引用的《梳理模型感知案例》对话，作为测试方向，不是自动适用的质量结论。

- 网页与 UI 的整体体验、视觉审美和细节异常。
- 系统日志中的异常信号和值得关注的模式。
- 《杀戮尖塔 2》剧本、事件和巧思的观众效果。
- AI 游戏主播和娱乐局的实时互动、幽默和节目效果。
- 特定游戏卡牌的视觉风格辨识。
- 代码生成 3D 游戏时的素材审美与整体观感。

这些任务共同包含一个风险。模型可以生成形式上完整的结果，却没有可靠的现实质量判断。更多自我反思可能只是在重复原有偏差。

## 验证规则

先区分结果的评价来源。

- **可客观复现**：使用测试、对照样本、日志回放、截图比对或规则检查。报告覆盖范围和未知。
- **依赖真实用户**：让目标用户实际操作，记录任务完成、困惑、停顿、反馈和行为，而不是只问“感觉如何”。
- **依赖受众效果**：使用盲评、真实播放或多轮受众反馈。内部 Agent 只能提出假设和候选解释。
- **依赖领域专家**：交给有决定权或专业资格的评审者。Agent 不代替签批。
- **评价标准尚未稳定**：先建立参考样本、失败对照和评价维度，不宣称已经通过。

## 元测试

当用户指出结果“不够好”时，不直接让同一个 Agent 自评改进。先记录：

- 用户指出的具体差异和原始结果。
- 现有评价基准能否解释该差异。
- 哪个外部样本、用户反馈或专家判断可以区分候选改法。
- 新版本是否由同一偏差来源评价。

如果改进前后只得到内部“更好”的判断，结论只能是“内部评价发生变化”，不能写成真实质量提升。

## 输出格式

感知验证至少交回：

```markdown
评价对象与版本：
目标评价来源：
评价方法：
实际观察：
与基准的差异：
已证实的问题：
仍属主观或未知的部分：
可支持的改进假设：
不能据此宣称的结论：
```
