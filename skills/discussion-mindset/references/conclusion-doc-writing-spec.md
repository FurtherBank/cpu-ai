# 研讨结论说明文档：写作规格

研讨（`discussion-mindset`）跑完、多个承重内容单元已单点封口之后——承重内容单元指一旦判错、后续结论就会跟着歪的关键判断点；单点封口指这些判断点已被逐个单独确认过、不再悬而未决（二者的完整定义见 `f-attention-budget-constraint`）——如果要把这一阶段的结论沉淀成一份**完整、可长期复用的说明文档**，按本规格写。

它只管一件事：怎么把**已经封口的研讨结论**写成给人读的文档。研讨本身怎么做（方向校准、灵魂点搜寻、隔离聚焦、单点封口）不归本规格管，那是 `discussion-mindset` 本体加 `f-attention-budget-constraint` 的事。

## 产出目标和定位

我们通过研讨得出的结论，一般是**高信息密度**，**高度理论化**的语言文字风格来表达的。
实测这种风格的表达会让其他主体很难做到能够直接的深度理解。  
因此，我们编写结论说明文档，除了写明结论内容本身外，还需要通过举合适例子的方式——通过叙事的形态，以**情境中具体发生了什么，走向了什么情况的方式**，让读者可以更容易的理解这个**完整的论述过程和结论体系**，本身是在讲什么，对应的不同情况会意味着什么。


## 具体写作规格

### 按读者动线组织，不照搬推导单元的输出

研讨阶段常把话题拆成多个承重单元分别封口，可能由多个 Subagent 各自产出一份结论。写文档时**不要**把这些单元的原始输出按产出顺序拼起来。要按读者的理解路径重排，典型顺序是：**这是什么 → 为什么它反直觉 / 为什么重要 → 怎么识别或怎么做 → 边界和例外**。

子单元的结论是原料，读者动线才是产物。同一个封口结论，在文档里出现的位置由「读者此刻需要它来理解什么」决定，而不是由它在研讨里被推导出来的先后决定。

### 叙事例子是承重内容，不是装饰（本规格的重点）

每一个阶段的**论述**，都需要配对应的**情境化叙事例子**，让抽象结论在具体场景里被读者认出来。一个合格的叙事例子满足：

- **是具体情境，不是概念复述**：有主体、有动作、有走向，读者能在脑里想象出画面。「某人在某处做了某事，然后发生了什么」，不是把结论换个说法再讲一遍。
- **从主体的第一手处境讲起，不做旁观式状态归纳**：开场就把读者放进主体的位置——他遇到了什么具体的事、听到 / 看到了什么具体的内容、在意什么、为什么在意。即使句子里有主体和动作，只要叙述始终站在外面对各方状态做抽象归纳（旁观式状态归纳：像填状态表一样罗列「A 已完成、B 尚未整理、C 可能不足」，读者想代入却找不到任何可想象的细节），本质上仍是概念复述，只是套了一层人物外壳。注意「第一手」指的是叙述姿态，不是人称：用第三人称同样可以写出第一手处境（「他因中暑住院，出院时只被告知……他最怕的是……」）；反过来，把状态归纳的句子改成「我」的口吻并不能让它合格。

  对照样例（同一个情境的两种写法）：

  ❌「出院团队已完成当次评估、给出常规恢复建议并安排随访；用户的经济压力、康养条件和『怕问题被忽视拖成后续风险』的具体担忧尚未被整理成下一次沟通可用的问题，随访时也可能只聚焦既定指标。」——有主体有动作，但全程是旁观式状态归纳：「具体担忧」到底是什么，读者不知道，代入不了。

  ✅「我因中暑住院，出院时医疗团队只给了『避免高温剧烈活动、最好居家静养、补充电解质』这类基本建议。但我经济压力大，虽然可以康养一段时间，最怕的是康养过程中出的问题被忽视，拖成之后还要额外折腾时间去应对的风险。所以我需要的是更全面的应对策略——比如格外注意体温、尿色与尿量，出现头晕、恶心、心悸、发热或精神倦怠时能识别并及时应对——而不是只被告知『休养后，某某指标会回归正常』。」——中暑住院、经济压力、怕小问题拖成后续负担，主体的处境和在意的点都具体在场，连「该注意什么」都落到了实际内容，读者能代入。
- **显形分叉**：把一件事情的发展「同一起点、不同走法 → 走向不同结局」这个分叉显式摆出来，而不是只讲一条正确走法。分叉本身就是让读者看懂「这一点在讲什么」的机制——读者是通过看到各种不同可能性的差别，才理解这个点在管什么。

叙事例子承重，所以在 `f-attention-budget-constraint` 的闸门下，每个关键例子都应作为承重内容单元对待：先确认它真的显形了目标分叉，再确认它没有为了生动而扭曲原结论。为了画面好看而牺牲结论准确，是这一体裁最典型的失败方式。

### 自造术语落白话注解

沿用研讨中产生的自造术语时，遵守 `writing-expression` 的造词契约：首次出现给定义，紧跟一行白话注解（「说白了就是……」）或一个微型示例；一个概念自始至终只用一个名字。

研讨内部为了高密度沟通造的命名，不要直接搬进面向读者的文档而不解释——研讨参与者脑里的语境，裸读者没有。

### 边界、置信与反例：不许为了收束而删

研讨结论几乎总带着反例、适用边界、未知项，以及当前解不掉又不能假装不存在的硬问题。这些**恰恰是文档最容易被误当「万能结论」而用错的地方**，必须保留并显式成节，通常包括：适用边界（哪些场景不管用）、置信分层（实证 / 推断 / 未知）、已知反例或残留问题。

不要为了让文档显得干净统一而压掉单点的复杂度。这与 `f-attention-budget-constraint` 整合层「不得为漂亮统一感回头压低任何单点的复杂度」同源：整合是关系判断的落笔，不是把粗糙抹平。

### 基本要求

- **档位**：默认按 `writing-expression` 的第二档（人类读的持久文档）处理；若要落进知识库长期复用或对外发布，按第三档处理，走该规则的落盘关口。

- **格式**：遵循 `markdown-writing` 的格式基本要求；产出文档中的**每个叙事例子各自用引用块整体包裹**，与正文论述区分开。

## 生产流程要注意

满足本规格开头的适用前提（研讨已跑完、结论已封口、需要沉淀成说明文档）、且研讨上下文较重（封口结论都在当前对话历史里）时，按以下方式产出：

1. **fork 一个 Subagent 承担写作**：用 `f-attention-budget-constraint` 的 fork 方式（cursor：`Task` 且 `resume: "self"`；codex：`fork_context: true`），让写作线程继承整段研讨历史，从而直接拿到全部单点封口结论，避免把大量结论重新塞进 prompt 时失真或遗漏。派发时在 prompt 里额外写清：产出目标和定位（一份完整说明文档）、落盘路径、读者与档位、以及「按本规格 `references/conclusion-doc-writing-spec.md` 写作」。
2. **写作线程走 `f-attention-budget-constraint`**：把文档的承重部分——核心定义、每个叙事例子、边界与置信声明、一句话总括——当承重内容单元，按其闸门与动作分档处理，而不是一路顺写到底。
3. **落盘关口**：第三档产物或对外发布物写完后，按 `writing-expression` 的落盘关口做冷读裸测；第二档做落笔自查。

如果研讨上下文很轻，或用户只要一小节说明，可以不 fork，直接在主线按本规格写。**fork 与否是成本权衡，写作规格本身不变。**

### 完成自检

- 每个核心结论都能在文档里找到对应的叙事例子，且例子从主体的第一手处境讲起、显形了分叉、能让读者认回它所对应的抽象结论。
- 自造术语首次出现都有白话注解，且一概念一名。
- 适用边界、置信分层、反例 / 未知项成节保留，没有为收束被压掉。
- 组织是读者动线，不是推导单元的顺序拼接。
- 所有结论都来自已封口的研讨判断，没有在写文档时新混入未确认的推导。
